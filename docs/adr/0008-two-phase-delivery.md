# ADR-0008：分两阶段交付——先做最小可用 Harness，再做可扩展平台

- 状态：已采纳
- 日期：2026-11-25

## 背景

原计划在第 04 章就引入插件内核，之后每一项能力都以插件形式实现。实际学习时发现：

- 还没有一个能跑的 Agent，就先学插件生命周期、依赖编排，概念过于抽象，很难理解它在解决什么问题；
- 一开始就设计扩展点，容易设计出用不上的抽象；
- 先把 Agent 做出来，才知道哪些地方真正需要扩展。

## 决定

**第一阶段（第 00–14 章）：最小可用 Harness（MVP）。** 一个能日常使用的桌面 Agent：流式对话、Agent 循环、工具、真模型、执行观测、护栏与审批、多会话、上下文管理、技能、待办、子代理、MCP。没有插件系统，所有能力写在 `liharness-core` 里。

**第二阶段（第 15–20 章）：完整 Harness。** 多模型管理、插件 SDK 与扩展点、插件宿主（外部 jar 热插拔）、插件市场、原生能力、打包发布与评测。

第一阶段的代码要为第二阶段留好边界：

1. `liharness-core` 不依赖 Spring；
2. 工具、提示词段落、事件都通过注册表加入，而不是在循环里写死；
3. `Tool` 接口从第 06 章起就放在独立的 `liharness-plugin-api` 模块里（只依赖 JDK），内置工具、MCP 工具（第 14 章）和第二阶段的插件工具共用同一接口。

## 后果

好的：
- 学到第 14 章就有一个完整可用的产品，可以先用起来
- 第二阶段的扩展点来自第一阶段的真实代码，不是凭空设计
- 每一章都能看到具体的效果

坏的：
- 第 16 章还要在 `plugin-api` 里补上 `Plugin`、`PluginContext`、钩子等类型，并把第一阶段里的几个接缝（`ToolGate`、`SystemPromptBuilder`、`ITurnEventListener`）提升为扩展点
