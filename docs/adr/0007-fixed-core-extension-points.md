# ADR-0007：固定内核 + 扩展点插件，插件不替换底层设施

- 状态：已采纳（取代 [ADR-0003](0003-framework-agnostic-microkernel.md)）
- 日期：2026-11-25

## 背景

ADR-0003 的设计是“万物皆插件”：模型适配、Agent 循环、会话存储、护栏、审批都做成可替换的插件，由一个微内核按依赖编排。

推演具体场景时暴露出几个问题：

1. **单选型服务的冲突。** 两个插件都提供 `ChatModel` 或 Agent 循环时，“用哪个”只能靠加载顺序或额外的装配配置决定，用户很难理解。
2. **替换后的一致性。** 提供者换了，依赖它的插件必须重新加载，否则会继续使用旧对象。为此需要依赖图、级联重载等一整套机制。
3. **真实需求在“加能力”，不在“换内核”。** 用户要的是“装一个做 PPT 的插件”“接公司内部系统”，属于增加工具和提示词；替换 Agent 循环只有做二次开发的开发者才需要，而他们可以直接改代码。
4. **对照同类产品。** Claude Code、Codex，以及扩展点式的 Java Harness 实现，插件都只能增加工具、技能、钩子、MCP 等能力，底层运行时是固定的；模型通过配置选择。只有 DeepSeek Harness 把循环和存储也做成插件，它服务的主要是拿它做底座的开发者。

## 决定

1. **内核固定**：模型适配与模型列表、Agent 循环、会话存储、上下文组装与压缩、护栏与审批主流程，由 `liharness-core` 实现，插件不能替换。
2. **内核按端口与适配器组织**：每一块仍是“接口 + 默认实现”，开发者改代码就能替换（例如 H2 换 PostgreSQL），但这不属于插件能力。
3. **插件只通过扩展点增加能力**：工具、提示词段落、钩子（固定时机）、事件订阅、技能。扩展点都是集合型的，多个插件共存，不需要选择“用谁”。
4. **插件之间没有依赖关系**，宿主不做依赖编排；插件只依赖 `liharness-plugin-api`。
5. **模型不是插件**：用户在设置页管理模型列表，选默认模型和会话模型。
6. 智能体内核与插件 SDK 依然**不依赖 Spring**（保留 ADR-0003 中这一条）。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 维持 ADR-0003 的微内核 | 单选型服务的冲突、级联重载带来的复杂度，对目标用户没有对应的价值 |
| 插件可替换内核，但用装配配置决定（类似 DeepSeek Harness 的 profile + patch） | 可行，但需要额外设计装配配置、冲突提示和回滚；放到以后，有真实需求再做 |
| 不做插件，只用 MCP | MCP 只能提供工具，无法提供钩子、提示词段落和事件订阅 |

## 后果

好的：
- 内核主链路始终是同一套代码，出问题好排查
- 插件 SDK 很小，插件作者容易上手
- 不需要依赖编排、提供者栈、级联重载
- 第一阶段可以完全不写插件系统，先把 Agent 做好

坏的：
- 想换 Agent 循环或存储的人必须改代码、重新打包
- 将来如果要开放“替换内核”，需要再设计一层装配配置（届时新开 ADR）
