# ADR-0010：会话存储改用 JSONL 文件

- 状态：已采纳（取代 ADR-0006）
- 日期：2026-11-26

## 背景

ADR-0006 计划用 H2 + Flyway 存会话。写第 10 章时重新评估：

- 会话的访问模式非常简单：**追加**新消息、**按会话整体读出**、列出会话。没有跨会话的查询、没有关联、没有更新；
- H2 带来了 Flyway 迁移、文件锁（同一时间只能一个进程打开）、数据库版本升级时的文件格式兼容等问题；
- 用户想看看“模型到底收到了什么”时，数据库文件打不开，JSONL 用任何文本编辑器都能看；
- Claude Code 等同类工具也用 JSONL 保存会话。

## 决定

1. 每个会话一个文件：`<数据目录>/sessions/<会话id>.jsonl`，每行一个完整的 JSON；
2. **只追加，不修改**：消息、改名、压缩（第 11 章的 `{"type":"compaction",...}`）都是追加一行；
3. 写入后 `FileChannel.force()`；读取时容忍最后一行写了一半（崩溃时可能发生），跳过它；
4. 读取时用 `HistoryRepair` 修复“只有工具调用、没有结果”的历史，保证不变量 2；
5. 会话 id 严格校验格式，防止路径穿越；
6. `ISessionRepository` 是领域层的仓储接口（`domain.session.adapter.repository`），`JsonlSessionRepository` 是基础设施层的实现（`infrastructure.adapter.repository`），都在 `liharness-core` 里，纯 Java，不依赖 Spring。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| H2 + Flyway（ADR-0006） | 见背景；对这个访问模式来说太重 |
| SQLite | 需要本地库，跨平台打包更麻烦；同样打不开看 |
| 一个大 JSON 文件 | 每次写都要整体重写，崩溃时可能丢掉整个文件 |

## 后果

好的：

- 零依赖、零迁移；用户可以直接查看、备份、分享会话文件
- 崩溃最多丢最后一行
- 压缩不丢原始记录：完整历史和“摘要 + 之后的消息”都能从同一个文件推导

坏的：

- 列会话要扫描目录，会话很多时变慢（第 10 章练习 3：加索引文件）
- 跨会话搜索需要自己实现（逐个文件扫描）
- 设置（`settings.json`）同样用文件，并发写入要自己加锁
